# Org Mode — making Arceus behave like a company, not a run queue

*2026-07-18 · study of [paperclip](https://github.com/paperclipai/paperclip) ("If OpenClaw is an
employee, Paperclip is the company") against the Arceus stack. Verbatim sources: paperclip
`doc/SPEC.md`, `doc/GOAL.md`, `doc/PRODUCT.md`. The finding in one line: our delegation
KERNEL is deeper than theirs, but our company only moves when a human submits a run —
paperclip's moves because every employee has a standing heartbeat and all work traces to a
goal. Most of what we need already exists in chorus and is simply never activated.*

## Why our system doesn't feel like an org

An org has three properties Arceus currently lacks at the product level:

1. **It runs when nobody is watching.** Paperclip fires a per-agent heartbeat on a schedule;
   the default CEO config is "review what your executives are doing, check company metrics,
   reprioritize, assign new strategic initiatives" — every cycle, forever. Our employees are
   dormant between human-submitted runs. The conductor's heartbeat pulses, but nothing
   *generates* wakes: no CEO review loop, no engineer backlog pull.
2. **Every task answers "why am I doing this?"** Paperclip enforces parentage to the company
   goal ("researching Granola's ads → Facebook ads → +100 signups → $2k revenue → $1M MRR").
   Our tasks have `goal_id` and `parent_id` columns, but delivery runs land goal-less and the
   why-chain is never shown.
3. **Work IS the communication channel.** Paperclip has no chat: delegation = create a task,
   coordination = task comments, an agent's inbox = assigned tasks + comments they're on,
   escalation = comment on the parent or reassign to your manager. We have decompose within
   delegation contracts and nothing else — no comments, no cross-team requests, no inbox.

Where we are AHEAD (do not import their weaker versions): typed delegation contracts with
bounded authority (depth/team/spend/professions), machine-verified TDD + review evidence,
independent system-verifier, RLS multi-tenancy, priced-per-beat cost ledger, formation
governance (CEO proposes → human applies atomically). Paperclip's crash-recovery stance
("surface stale work, never silently fix") we already share (watchdog → Ops view → recovery
actions).

## Gap table

| Paperclip behavior | Arceus today | What's missing |
|---|---|---|
| Per-agent heartbeat with role loop (CEO review cycle, engineer backlog pull) | `org.routines` facade + `chorus.cron` + `ceo_plugin` routines EXIST, never wired by podium | Activation: default routines at hire, cron firing in the conductor's pulse |
| Task → … → company-goal parentage, always | `goal_id`/`parent_id` columns exist; delivery runs land goal-less | Goal required (or defaulted) at the run door; why-chain in cockpit |
| Tasks + comments as the only channel; inbox = tasks + comments | `send_message`→Wake exists; no comments | `task_comment` table + tools (`comment`, inbox in beat brief) |
| Cross-team requests, acceptance rules, reassign-to-manager escalation, request depth | `request_depth` tracked; `staffing_request` exists | An `assign-outside-team` path + the acceptance/escalation rules in role briefs |
| Board = live control surface (pause/resume agent, edit/reassign any task, budgets at every level) | approve/reject plans, hire/terminate, cancel run | pause/resume employee door; task reassign/edit doors; budget doors |

| Org templates: export/import company configs | Workforce export door exists | Import door + template (structure-only) vs snapshot modes |

## Adoption plan (each phase independently shippable)

**OM-1 — Standing heartbeats (the big one).** At hire, provision the role's default routine
(chorus `RoleRegistry` plugins already carry routine definitions; the CEO plugin has
`_routines.py`): CEO — review goal tree health, reports' last beats, spend vs budget,
re-prioritize, open staffing requests; engineer — claim the highest-priority assigned task.
Podium: the conductor's per-company pulse also fires due `chorus.cron` schedules; a cockpit
Routines panel (list/pause/resume — the facade verbs already exist). Result: submit ONE
formation run and the company keeps operating.

**OM-2 — The why-chain.** Runs door: `goal_id` optional param, defaulted to the company's
root goal; delegation already threads it. Cockpit Work/Runs views render the parentage chain
("because → because → goal"). Enforcement note in briefs: work with no goal lineage is
questioned by the manager routine, mirroring paperclip's acceptance rule 3.

**OM-3 — Comments as coordination.** Engine: `task_comment` (chorus DDL delta), `comment` +
`read_comments` tools in every manifest, comments injected into the beat brief for assigned
tasks (the inbox). Cross-team: `submit_task` outside the contract tree becomes a REQUEST
(todo, `request_depth+1`, acceptance rules in the brief: do it / block it / reassign to your
manager with a comment — never self-cancel). Cockpit: comments on the Work board.

**OM-4 — Board as control surface.** Doors + cockpit buttons: pause/resume employee
(chorus `EmployeeStatus` supports it), reassign task, edit priority, per-employee/company
budget PATCH; budget ceiling → auto-pause employee + Ops alert (event exists). Billing-code
attribution: cost_event already carries run→task; roll up to the requesting task's lineage.

**OM-5 — Templates & capabilities.** Employee `capabilities` blurb (shown in `team_read`,
set at hire/formation); workforce import door (template vs snapshot per paperclip's two
export modes — our export bundle already matches "template").

## Sequencing

OM-1 alone changes the felt behavior from "run queue" to "org". OM-2/3 are the alignment and
communication substrate the routines then exploit. OM-4/5 are product surface. Estimated
engine work is small because chorus anticipated all of it (routines, cron, wakes, budgets,
request depth) — the gap is podium/cockpit activation, briefs, and one new table (comments).
